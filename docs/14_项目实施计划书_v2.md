## 一、项目概述

### 1.1 一句话定义

把物流企业的运单数据翻译成碳排放量，再翻译成成本与减排方案，在一个离线可运行的本地网页上完成决策推演。

### 1.2 项目定位

| 维度 | 定位 |
|---|---|
| 赛题层面 | 京采命题"运输减碳方案设计"——用数据与算法给出可量化的减碳路径 |
| 学科层面 | 商业逻辑（会计 × 金融）× 数据科学 × 软件工程的交叉实践 |
| 能力层面 | 商业逻辑初创、数据建模、算法开发、软件交付的全流程训练 |
| 交付层面 | 轻量、离线、可复算、可解释——双击脚本即可运行 |

### 1.3 核心目标（按优先级）

1. **算得对**：碳排数据与既有计算文件对拍一致（33,214 段 / 4,690,435.81 km / 14.67 g/s）
2. **跑得稳**：`python -m src.pipeline` 一键复算；前端只读不卡；静态演示数据兜底
3. **说得清**：每个数字可追溯来源，实测与假设分离标注
4. **看得懂**：五个页面各回答一个决策问题，界面即论证

### 1.4 明确不做（范围边界）

发票 OCR 全链路、分布式/微服务/区块链、碳金融产品、低空无人机、多 Agent 协同——只写入未来展望，本阶段不开发。

## 三、技术路线（扁平四文件架构）

### 3.1 数据流（三段 + 只读前端）

```
① 原始数据   data/raw/ 三张表（含隐藏表，不入 Git）
        ↓  src/preprocess.py：读取 → 三表关联 → 清洗 → 合成唯一宽表
② 宽表       data/processed/wide_data.parquet（含碳核算所需全部字段）
        ↓  src/optimizer.py：排放因子查表 + 线性内插 → 段级碳排
③ 碳排明细   data/processed/baseline_carbon.parquet
        ↓  src/evaluator.py：高排放热点 / 替代方案 / 成本效益
④ 分析决策   data/processed/final_report.parquet
        ↓  src/pipeline.py：统一调度 + 台账/报表打包（出口对拍校验）
⑤ 台账展示   app/：五个页面只读展示（绝对不调用核心算法）
```

### 3.2 三条铁律

1. **文件越少，找 Bug 越快**：路线不对，只查 `preprocess → optimizer → evaluator` 三个文件；
2. **一次准备、全程只读宽表**：清洗与匹配只在 preprocess 做一次，算法层只看宽表，不再回头碰原始数据；
3. **前端只读不算 + 静态数据兜底**：演示不依赖实时计算，不会卡死。

### 3.3 对拍闸门（简化版）

- **preprocess 出口**：33,214 段 / 4,690,435.81 km / 速度有效样本 33,213 / 均速 49.57 km/h
- **optimizer 出口**：30 t → 14.67 g/s（±0.01）；VSP=3 偏差 12.68%
- **pipeline 出口**：任一校验超差即中断（退出码非 0）——保留"闸门"叙事，去掉执行器、缓存与契约文件

### 3.4 技术栈（锁定，不讨论替代方案）

Python 3.10+ ｜ Streamlit（只读结果表）｜ Pandas + Parquet ｜ 图表用 Plotly 或 Streamlit 原生（二选一，全项目统一）｜ venv + `requirements.txt` ｜ Git + GitHub

> 相对 v1.0：去掉 SQLite（结果全部落单文件 parquet）、去掉执行器框架与节点契约文件。

## 结语

这个项目最难的不是算法，是四名学生把一条数据流从头到尾不出错地串起来。

扁平四文件架构让每个 Bug 只可能藏在三个地方（preprocess → optimizer → evaluator）；对拍闸门让每一步都有可验证的数字判据，不达标就不许往下走。

**先保证对，再追求快；先立契约，再谈效率。**
