## 0. 一句话结论

**要，用高德；但不是"接一个 API"这么简单，而是加一层"路线情景"**：
高德只出"路"（距离/时长/坐标串），**选哪条路、这条路排多少碳、λ 一动推荐换不换，全部由我们自己写函数算**。
地图在线用高德 JS API（合规底图），断网回退现有 Plotly 离线底图；
碳核算分三层（L0 基准 / L1 路线情景 / L2 λ 决策），**E₀ = 4,502,042.41 kg 的主口径永远不动**。

### 1.2 与既有纪律的关系（四条铁律全部保持）

1. **业务逻辑仍只有 4 个 src 文件**：路线预取放 `tools/`（工具脚本），`optimizer.py` 只**增加一个只读结果表的函数**（O8），pipeline 只**增加一个可选段**（`--with-routes`，缺表自动跳过）。

## 5. 函数设计：高德出"路"，我们写"决策"

以下 9 个函数全部由我们自己撰写（高德不提供任何决策能力）。签名即接口契约，PR 标题按蓝图约定写 `feat(T7): route_fetch 批量算路与缓存`。

### 5.1 `tools/route_fetch.py`（预取层，网络 I/O）

```python
def load_key() -> str:
    """env → config/amap_key.txt → 占位符。占位符=演示回退模式，不报错。"""

def geocode(name: str, city_hint: str = "") -> tuple[float, float] | None:
    """地名 → GCJ-02 坐标。本地 CITY 表优先；缺失才调 /v3/geocode/geo。
    失败返回 None（调用方回退离线坐标），遵守工程师建议 #1 不抛异常。"""

def fetch_driving(origin: tuple[float, float], dest: tuple[float, float],
                  strategy: int = 32) -> dict | None:
    """单 OD 驾车规划 /v3/direction/driving。
    strategy：32=默认(时间短/距离短/躲避拥堵综合)、34=避免拥堵、35=不走高速。
    返回 {distance_km, duration_min, toll_yuan, traffic_lights, polyline, steps}；
    失败/超时(10s)/配额耗尽 → None。"""

def batch_fetch(od_pairs: list[dict], qps: float = 3.0, cache_path: Path = ...) -> pd.DataFrame:
    """批量算路 + 限流(令牌桶) + 指数退避重试(最多3次) + 本地 parquet 缓存。
    已有缓存的 od_key 直接跳过——第二次运行零 API 调用。
    任何单点失败只跳过该 OD，不影响整批。"""

def offline_route(origin: tuple[float, float], dest: tuple[float, float]) -> dict:
    """无网回退：haversine 直线距离 × 1.28 绕行系数，duration 按 50 km/h 反推。
    与 docs/20 §2『距离缺失→绕行系数 1.28』完全同口径，保证口径一致。"""
```

### 5.2 `src/optimizer.py`（O8 动态碳核算，只读结果表）

```python
def route_carbon(seg: pd.DataFrame, route: pd.DataFrame) -> pd.DataFrame:
    """路线情景双轨碳核算。输入段表 + route_od.parquet，输出追加列：
      - route_km / route_min：该段所在 OD 的路线距离/时长（缺失回退宽表值并打 flag_route_est）
      - kg_co2_route_legal：法定轨 = route_km × factor_gkm（常因子，口径不变）
      - kg_co2_route_phys：物理轨 = 用 route_min/route_km 得路线平均速度 → VSP 档位 → er_gs × 时长积分
      - delta_pct_route：路线情景 vs 宽表基准的双轨偏差（正负都要）
    因子仍从 FACTOR_BY_CLASS_LOAD 查——『因子是口径不是数据』的边界不变。"""

def route_select_by_lambda(scenarios: pd.DataFrame, lam: float) -> pd.DataFrame:
    """λ 联合目标选路/选车：score = 运营成本(元) + lam × 碳排(t)。
    运营成本 = 能耗成本(油/电) + 过路费(路线自带) + 时间成本(路线时长 × 时薪假设，标注为展示口径)。
    输出每 OD 的推荐路线/推荐车型，λ 变则推荐变——这就是首页旋钮的意义。"""

def route_constraint(route: pd.DataFrame, vehicle: dict) -> dict:
    """C1/C4 与路线直接挂钩：route_km ≤ 可用续航 × 0.8；线路 30km 缓冲区补能(离线站点表)。
    复用 docs/20 §7 规则文本，不在前端重算。"""
```

### 5.3 三个关键实现细节

**① 平滑（不卡）**：`batch_fetch` 只跑一次（310 个 OD，QPS 3 约 2 分钟），之后全部读缓存；pipeline 加 `--with-routes` 才触发重算；前端永远只读 parquet，**答辩现场零 API 调用**。

**② 流畅（体验）**：预取顺序按 OD 碳排降序——前排热点先有数据；单 OD 超时 10s 即弃；失败 OD 自动落到 `offline_route`，并在 `data_quality.json` 记 `route_estimated` 计数，前端黄框提示（沿用现有 flags 组件）。

**③ 坐标系**：高德返回即 GCJ-02，前端高德底图直接用；本地 CITY 表是离线近似坐标（仅回退演示用，已在表中注明）；**禁止**把 GCJ-02 坐标当 WGS-84 用，也禁止反向偏移后自绘。

## 6. 动态碳核算：三层口径（对拍纪律不破）

### 6.1 三层定义

| 层 | 名称 | 数据源 | 是否可改 | 用途 |
|---|---|---|---|---|
| **L0** | 基准核算（现状） | 宽表实测里程 × 因子 | **永不动**。E₀ = 4,502,042.41 kg | 第 1 页、台账基准行、全部对拍 |
| **L1** | 路线情景 | 高德路线距离/时长 × 同一因子表 | 可增不可改主口径 | 回答"按推荐路径走，碳账差多少" |
| **L2** | λ 决策情景 | L1 + 运营成本 + λ | 可增 | 回答"λ 一变，推荐换不换" |

### 6.2 为什么 L0 不动（这是本方案的对拍生命线）

宽表里程是**实际行驶里程**（运单回传），高德路线是**推荐路径距离**。两者本就该接近（差的是绕行、维修、实际道路选择），差值本身就是信息（路径优化空间），**不是误差**。所以：

- L1 只做**差量分析**（Δkm、Δt、Δ碳），不覆盖、不平均进 E₀；
- 第 1 页 E₀ 永远是 L0；动态面板明确标注"路线情景口径"；
- 台账仍只记 L0（三行六字段不变，`docs/15` 的"台账总碳=首页总碳"闸门不受影响）。

### 6.3 新增闸门软校验（S1–S3，仅 `--with-routes` 时启用）

| # | 校验项 | 目标 | 不通过时 |
|---|---|---|---|
| S1 | 路线情景 vs 宽表里程：中位 \|Δkm\|/km | ≤ 10% | 打印超差 OD 清单，退出码 1（防止路线数据源错乱污染结论） |
| S2 | 路线碳 vs 基准碳（同 OD 聚合） | 同向偏差、无系统性漂移 | 同上 |
| S3 | route_od 覆盖：热点 OD（碳排 TOP 300）缓存率 | ≥ 95%（其余允许离线回退） | 警告不阻断 |

## 8. 平滑与降级链（任何一步失败都有数可演）

```
高德 REST 批量算路
   │ 成功 ──> route_od.parquet（真路线）          → L1/L2 全量
   │ 单 OD 失败/超时
   │        └─> offline_route(haversine×1.28)     → 该 OD 打 flag_route_est，黄框
   │ key=占位符 / 完全无网 / 配额耗尽
   │        └─> 全量 offline_route               → 页面标注"离线估算路线"
   │ 连 CITY 坐标都缺
            └─> 跳过 route 段（pipeline 打印 SKIP）→ 回 L0，五页照常演示
```

**永不出现的状态**：白屏、灰图、Exception、页面卡死。这与工程师建议 #1/#9（不许抛异常、静态兜底）完全一致。
