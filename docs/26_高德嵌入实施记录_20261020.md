## 3. 数据流与三层口径

```
tools/route_fetch.py ──高德 REST──> route_od.parquet（310 条热点 OD）
        │ 失败/无 key                    ├─ 真路线（amap_rest）
        └─> offline_route()               ├─ 离线兜底（haversine×1.28）
           （haversine×1.28）             └─ 坐标缺失（missing_coord，不编数字）
                                            │
              src/optimizer.py O8 ──────────┤
              route_carbon()  ─────────────┴─> route_carbon.parquet（L1 双轨）
              route_select_by_lambda() ─────> route_select.parquet（L2 λ 推荐）
                                            │
              app/ 前端只读 ◄────────────────┘
```

| 层 | 口径 | 状态 |
|---|---|---|
| **L0** | 宽表实测里程 × 因子 | **永不动**。E₀ = 4,502,042.41 kg，闸门精确命中 |
| **L1** | 高德路线距离/时长 × 同一因子 | 只做差量分析，不覆盖 E₀ |
| **L2** | L1 + 运营成本 + λ | 展示口径（时薪/油价/电价是假设值） |

## 4. 实施中踩到的四个真问题（都记在这里，别再踩）

### 4.1 段表 `od_key` 是城市级，路线表是网点级

- 段表 `od_key` = "上海|深圳"（城市级），`od_site` = "上海茸华路营业部|上海车墩集货分拣中心"（网点级）；
- 路线表是网点级的 → **连接键必须用 `od_site`**；
- 修法：`optimizer._segment_join_key()` 优先 `od_site`、缺失回退 `od_key`；
  `tools/route_fetch.py` 的 `ROUTE_COLUMNS` 同时输出 `od_key` 与 `od_site`。

### 4.2 `_short_city_names` 剥掉"州"字 → "苏州"变"苏"

离线兜底靠网点名前缀解析城市（"哈尔滨分拣中心" → "哈尔滨"）。
最初把"市/州"当行政后缀剥离，结果 **"苏州"→"苏"、"广州"→"广"**，前缀匹配全废、坐标大面积 missing。
**修法**：只剥离真正的行政后缀（`地区/特别行政区/自治州`），**不剥"市/州"**。

### 4.3 坐标缺失时 haversine 会算出上万公里

"德州齐河散货分拣中心"在宽表里坐标全是 NaN（该城市只作为终点出现、坐标未回填）。
原实现拿 (0,0) 当坐标算 haversine → **15,696 km** 的荒谬距离，比"没有路线"糟糕得多。
**修法**：`offline_route()` 坐标缺失时返回空字典，调用方标 `missing_coord`、
由引擎层回退宽表实测里程。**宁可标缺失，也不给错数字。**
（联网时这类网点由高德地理编码补全——这正是要配 Web 服务 key 的原因之一。）

### 4.4 "命中路线表"和"该路线是离线估算"是两个概念

最初用 `flag_route_est` 一个标记兼两用，导致"命中率 0%"的误判。
**修法**：拆成两个标记——
- `flag_route_hit` = 1：该段命中了路线表；
- `flag_route_est` = 1：该段的路线是离线估算/坐标缺失。
