# 用户数据输入规范

**系统名称：** 碳慧智算物流碳感知智能决策系统 V1.0  
**文档路径：** `docs/42_用户数据输入规范.md`  
**适用版本：** V1.0  
**文档状态：** 初稿，待与 `tools/import_data.py` 的最终输入契约联调确认

## 1. 目的与适用范围

本文规定 V1.0 物流碳排放核算与诊断流程所需数据的文件组织、工作表、字段、单位、校验、异常处理和隐私要求。本文用于统一用户填写的 Excel 模板、数据导入校验程序及后续预处理流程。

V1.0 采用本地文件输入和命令行校验方式；本规范不要求新增前端上传页、登录或在线注册功能。

**重要约定：** 本文区分“用户模板字段”“赛题原始附件字段”和“程序内部字段”。字段名称可以不同，但必须通过明确映射转换；不得仅因字段名称相似就默认含义、单位或业务口径完全一致。

## 2. 输入方式与目录结构

### 2.1 赛题原始附件输入方式

项目现有数据字典记录的赛题输入文件为：

- `data/raw/命题2数据附件1-2023年的订单数据和运单数据.xlsx`
  - `订单数据`：订单号、运单号、重量、体积、包裹数、发货/收货地点、妥投时间等。
  - `运单数据`：运单号、车牌、车型、里程、封车/解封车时间、起终点网点等。
- `data/raw/命题2数据附件2-运输车辆的核心信息.xlsx`
  - `Sheet2`：车型种类、燃油类型、车辆载重目录。
  - `Sheet1` 为隐藏的 ECLP–TMS 桥接表；按照现有数据字典，它不是当前订单与运单直接关联的必经键。

原始附件名称以实际提供的文件为准。若文件名与上面示例不同，应由导入程序根据配置或明确的参数指定，不应静默选取不相关文件。

### 2.2 标准化模板输入方式

为方便用户填写，团队任务书要求另行提供 `templates/数据输入模板.xlsx`，其中包含以下三张工作表：

1. `订单`
2. `运单`
3. `车辆`

每张工作表包含一行表头和一行虚构示例数据。模板示例必须明显标记为演示数据，不能使用真实运单、车牌、客户或发票信息。

标准化模板是便于用户输入的格式，不等同于赛题原始附件的原始结构。导入程序必须明确支持该模板，或明确告知用户当前仅支持原始附件格式；在完成适配前，不得声称两种格式可以直接互换。

### 2.3 目标运行流程

```text
data/raw/ 中的输入 Excel
        ↓
python -m tools.import_data --validate
        ↓
校验通过后执行数据处理
        ↓
python -m src.pipeline
        ↓
python -m streamlit run app/app.py
```

`tools/import_data.py` 的 `--validate`、`--input`、`--report` 参数及退出码属于任务书规定的目标接口。使用前应确认相应程序已合并到当前分支并通过测试。不得将尚未实现或未验证的命令描述为已可用功能。

## 3. 字段规范

### 3.1 通用规则

- Excel 第一行为列名，不应合并表头单元格。
- 列名应与模板保持一致；如果导入程序支持别名，别名应在程序中显式登记。
- 编号、运单号、订单号、车牌号、车型编码等标识字段按文本处理，避免 Excel 自动转换格式、丢失前导零或将长编号转为科学计数法。
- 日期时间应为 Excel 可识别的日期时间值，或程序明确支持的日期时间文本格式。
- 数值列不得在数字中混入单位文本；单位写在表头或本规范中。
- 空白值应保持为空，不得使用 `0`、`无`、`未知` 等字符串代替缺失值，除非字段规则明确允许。
- 不得为填满字段而编造发票、客户或业务记录。

### 3.2 订单 Sheet

订单表用于描述订单侧的货物和订单信息。字段以现有赛题数据字典及预处理逻辑为依据；具体模板表头应与导入程序最终契约保持一致。

| 建议标准字段 | 含义 | 类型/单位 | 要求与校验 |
|---|---|---|---|
| `order_number` | 订单号 | 文本 | 有源订单号时填写；保留原始标识，不得伪造 |
| `waybill_number` | 运单号 | 文本 | 必填；用于与运单表按运单号精确关联 |
| `shipper_city` | 发货城市 | 文本 | 建议填写；缺失时应报告，不得无依据推断 |
| `receiver_city` | 收货城市 | 文本 | 建议填写；缺失时应报告，不得无依据推断 |
| `total_weight_kg` | 订单重量 | 数值，kg | 如提供，必须为可解析数值且不得为负数 |
| `total_volume_cm3` | 订单体积 | 数值，cm³ | 如提供，必须为可解析数值且不得为负数 |
| `total_pieces_parcel` | 总包裹数 | 数值，件 | 如提供，应为非负整数；缺失与真实 0 必须区分 |
| `complete_time` | 妥投时间 | 日期时间 | 可为空；非空时应可解析 |

上述标准字段名是面向模板的建议命名。原始赛题附件中的中文表头或英文/中文混合表头应通过映射转换，不能要求用户擅自修改原始赛题数据。

### 3.3 运单 Sheet

运单表是物理运输路段识别和里程、时间分析的主要来源。

| 建议标准字段 | 含义 | 类型/单位 | 要求与校验 |
|---|---|---|---|
| `waybill_number` | 运单号 | 文本 | 必填；应可与订单表关联；重复记录需报告 |
| `vehicle_number` | 车牌/车辆标识 | 文本 | 必填；用于物理行程识别和去重 |
| `vehicle_type_name` | 车型名称 | 文本 | 必填；需与车辆表车型目录匹配 |
| `distance_km` | 实际行驶里程 | 数值，km | 必填；应为可解析数值且大于 0 |
| `departure_time` | 封车/发车时间 | 日期时间 | 必填；必须可解析 |
| `arrival_time` | 解封车/到达时间 | 日期时间 | 必填；必须可解析，且不得早于发车时间 |
| `departure_site_name` | 发货/封车网点 | 文本 | 应填写；用于线路分析 |
| `arrival_site_name` | 收货/解封网点 | 文本 | 应填写；用于线路分析 |
| `speed_kmh` | 平均速度 | 数值，km/h | 可选；仅在来源确实提供时填写，并注明来源 |

任务书将发货/收货网点列为线路分析必需信息。若实际数据只提供城市或其他起终点字段，应在导入报告中明确记录，不得把城市自动等同于具体网点。

### 3.4 车辆 Sheet

车辆表用于提供车型目录和车辆属性，尤其是车型匹配、燃料类型和载重口径。

| 建议标准字段 | 含义 | 类型/单位 | 要求与校验 |
|---|---|---|---|
| `vehicle_type_name` | 车型名称/车型种类 | 文本 | 必填；应与运单表车型名称匹配 |
| `fuel_type` | 燃料类型 | 文本 | 若源数据提供则填写；不得无依据替换 |
| `vehicle_load` | 车辆登记载重 | 数值，按源表口径 | 若提供必须可解析；需记录原始单位及口径 |
| `mass_basis` | 载重口径 | 文本/枚举 | 建议填写；区分载质量、整车总质量、准牵引总质量等口径 |

**载重口径注意事项：** 原始车辆表中的“车辆载重”可能对应不同物理口径，不应直接当成统一的有效载荷或排放因子输入。应保留源值，并由系统现有车型映射规则确定核算类别；无法判断时应标记待复核。

### 3.5 字段映射说明

现有 `src/preprocess.py` 包含部分内部字段别名映射，例如：

| 内部字段 | 当前代码中可识别的部分别名示例 |
|---|---|
| `waybill_no` | `waybill_no`、`waybill_number`、`运单号`、`运单编号` |
| `order_no` | `order_no`、`order_number`、`订单号`、`订单编号` |
| `plate` | `plate`、`plate_no`、`车牌`、`车牌号`、`车辆牌照` |
| `vehicle_type` | `vehicle_type`、`vehicle_type_name`、`车型`、`车型名称` |
| `dist_km` | `dist_km`、`distance_km`、`里程`、`行驶里程`、`实际行驶里程` |
| `depart_ts` | `depart_ts`、`发货时间`、`封车时间`、`起运时间` |
| `arrive_ts` | `arrive_ts`、`到达时间`、`解封时间`、`签收时间` |

该表只列出当前预处理代码中的部分别名，不代表输入校验程序已经实现相同的识别能力。新增或修改模板列名时，应同步更新导入程序、测试和数据字典。

## 4. 数据关联与去重

1. **订单与运单关联：** 以去除首尾空格后的运单号进行精确关联。订单号和运单号是不同字段，不得互相替代后再宣称关联成功。
2. **车型关联：** 运单车型名称应与车辆表车型目录匹配。应分别报告车型目录匹配率和基准核算车型映射覆盖情况；两者不是同一指标。
3. **运单重复检查：** 检查运单号重复情况，并统计去重前记录数、重复记录数和去重后物理路段数。相同运单号不必然代表完全相同的物理路段，去重规则应结合车辆标识、里程、时间及起终点。
4. **保留追溯能力：** 清洗或去重结果应尽可能保留源文件名、工作表名和原始行号，便于回查。
5. **缺失值处理：** 原始缺失必须保留缺失标记。不得把缺失重量、体积或包裹数填为 0 后再当作真实零值参与分析。
6. **发票字段：** 当前数据字典记录的赛题原始附件不包含发票号、发票状态或发票金额。没有真实发票来源时，应保持为空或标记为“不适用/未提供”，不得构造发票金额。

## 5. 输入校验规则

### 5.1 文件与工作表校验

- 文件必须可读取，文件格式必须受程序支持。
- 必须识别所需工作表；缺少工作表时，报告文件名和工作表名。
- 必填列缺失时，报告文件名、工作表名和列名。
- 不得在无法识别输入文件时静默改用演示数据并将结果当作真实赛题结果。

### 5.2 字段与业务校验

- 运单号、车辆标识、车型名称等必需标识不得为空。
- 里程必须为可解析数值且大于 0。
- 重量、体积等数值字段必须可解析；负值应报错或单独标记，不能静默修正。
- 发车时间、到达时间必须可解析；到达时间早于发车时间属于阻断性错误。相同时间应至少标记为异常并由业务规则决定是否阻断。
- 速度异常应单独标记并报告，不得静默覆盖原始速度。若源数据无速度列，按里程/正运输时长反算的速度必须标记为“计算值”，不能标记为实测值。
- 必须报告运单重复数量、去重后物理路段数量、订单—运单关联率及车型目录匹配率。
- 对关联率、匹配率的最低阈值，应由团队在 `import_data` 实现和测试中明确配置；本规范不擅自设定任务书未规定的数值阈值。

### 5.3 错误级别

- **FAIL（阻断错误）：** 文件不可读、必需工作表或必需列缺失、关键字段不可解析、里程非正数、时间倒挂等导致无法可靠继续处理的问题。
- **WARN（警告）：** 重复运单、异常速度、部分车型未匹配、非关键字段缺失、需要人工复核的载重口径或估算值等。警告是否允许继续，应按具体规则决定，并在报告中保留明细。

## 6. 错误提示格式

错误信息应尽量包含文件、工作表、行号、列名、错误原因和建议操作。建议格式如下：

```text
[FAIL] 附件1 / 运单数据：缺少列“实际行驶里程（km）”
[FAIL] 第128行：arrival_time 早于 departure_time
[WARN] 检测到重复运单：共 N 条，请核对去重前后记录数
[WARN] 存在车型未匹配车辆目录：共 N 条，请检查车型名称
```

上例中的行号和 N 为格式示例，不代表当前运行结果。实际报告必须填入程序检测得到的真实数量和行号。

## 7. 校验命令、报告与文件保护

任务书规定的目标命令为：

```bash
python -m tools.import_data --validate
python -m tools.import_data --input data/raw --report data/processed/input_report.json
```

目标退出码约定：

- `0`：校验通过。
- `2`：输入错误，例如缺列、时间错误或关联率未达到团队设定阈值。
- `1`：系统错误，例如文件读取失败或依赖异常。

**实现状态说明：** 上述命令和退出码来自团队任务书。提交本规范时，必须由负责 `tools/import_data.py` 的开发者确认实际参数和行为与本节一致；如果实现不同，应先协调代码与规范，不得只修改文档来掩盖差异。

处理保护要求：

1. 校验阶段不应修改原始输入文件。
2. 若存在阻断性错误，不得覆盖 `data/processed/` 中已有的有效结果，也不得留下被误认为完整的新结果。
3. 报告文件应区分通过、警告、失败，并记录输入文件、校验时间和问题明细；报告中不得包含不必要的完整车牌、客户或发票信息。
4. 只有输入校验通过并明确执行处理流程后，才允许生成新的处理结果。
5. 处理完成后应记录数据来源是竞赛真实数据还是演示数据，禁止把演示数据结果作为真实赛题核算结果。

## 8. 隐私与数据合规

- 不得将真实运单明细、完整车牌号、客户身份信息、发票号码、发票金额或其他可识别业务主体的数据提交到公开 GitHub 仓库。
- 对外展示、测试和文档示例应使用虚构数据；如需演示，应使用合成数据或经过充分脱敏的数据。
- 对已进入公开仓库的敏感数据，应与仓库负责人共同评估：停止继续传播、移除当前版本中的敏感文件、必要时清理 Git 历史，并按团队要求保留受控备份。仅删除当前文件不代表历史版本中的数据已被清除。
- 若真实凭据或访问密钥曾被提交，应立即撤销或轮换，不应只从文件中删除。
- 共享文件应遵循最小必要原则；报告和日志只保留排查问题所必需的信息。
- 本文不声称仓库已完成历史清理或数据脱敏；实际处置结果需由负责人检查并记录。
