## 1. 为什么做这个功能：链路里发票字段已全线贯通，只是全空

实测 `data/processed/` 的真实结果表：

```
wide_data.parquet        invoice_ok = -1（全行）   invoice_amount = 100% NaN   invoice_no = 全空
baseline_carbon.parquet  invoice_ok = -1（全行）   invoice_amount = 100% NaN   invoice_no = 全空
```

`src/preprocess.py:1101-1115` 里有一个**休眠分支**：

```python
# ---- 发票：只有原始输入确实包含发票字段时，才估算"未匹配发票"；
# 竞赛附件没有发票字段时必须保持 NaN / -1，不能凭空生成金额。
invoice_source = "invoice_amount" in raw.columns or "invoice_ok" in raw.columns
if invoice_source:
    ...未匹配的按同 vclass 历史 元/公里 中位 × 里程 → flag_estimated
else:
    work["invoice_ok"] = -1
    work["invoice_amount"] = np.nan
```

赛题附件不含发票字段 → 走 else 分支 → 发票列全线留空。
**`invoice_source` 就是发票识别的接口对接点**：补上发票来源后，这条分支自动激活，金额变真实值、`fill_invoice` 变成实际未匹配数、宽表→段表→热点→台账/披露全链路自动继承。

> 与 `docs/42 §4.6` 一致：「没有真实发票来源时，应保持为空或标记为"不适用/未提供"」——
> 现在正是"没有来源"，所以留空是对的；本功能的作用是**把来源补上**，而不是绕过这条纪律。

## 3. 业务逻辑：两轨交叉校验（本功能的核心价值）

**油量是实测值，因子表是估算值。两者的正确关系是交叉校验，不是替换。**

| 轨 | 公式 | 性质 |
|---|---|---|
| **油量直算轨** | `油量 × 柴油因子(TTW 2.63 + WTT 0.53)` | 实测（票面加注数量） |
| **里程因子表轨** | `里程 × 因子表(车型, 载重)` | 估算（与第 1 页 E₀ 同源） |
| **油量反推里程** | `油量 ÷ 油耗基准(L/100km)` | 假设值驱动 |

判读逻辑（`_cross_verdict`）：

| 差异 | 判读 |
|---|---|
| ≤ ±10% | 两轨一致，互证通过 |
| ±10~25% | 有偏差，建议核对油耗基准与里程 |
| > +25% | 油量轨显著高：查车型错配 / 里程错报 / 油耗异常 |
| < −25% | 里程轨显著高：查里程虚报 / 油量识别偏低 |

**差异本身就是诊断信号**——这才是发票功能真正的业务价值。

> ⚠️ **油量不该进 E₀ 主账**。两条理由：
> ① `docs/20 §11` 纪律 3：演算结果不得进 kpi/gate；动 E₀ 会让闸门目标值立刻变红。
> ② 因子表口径与油量口径是**两种不同性质**的证据，替换会丢掉互证能力。
> 若将来要让油量进正式口径，必须同步：字段登记 `docs/07` + `src/schema.py` 契约 + `flag_estimated` 留痕 + 披露 + 闸门**两套来源互证**项（`docs/28` D6 教训：目标值与被验值不得同源）+ 全量重跑对拍。

## 5. MiniMax 调用规范（含三个必踩的坑）

### 5.1 请求格式（OpenAI 兼容）

```python
POST https://api.minimax.io/v1/chat/completions      # 国内站换 api.minimax.cn
Authorization: Bearer <key>
Content-Type: application/json

{
  "model": "MiniMax-M3",
  "messages": [{"role": "user", "content": [
      {"type": "text", "text": EXTRACT_PROMPT},
      {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,<b64>", "detail": "high"}}
  ]}],
  "max_completion_tokens": 800,
  "thinking": {"type": "disabled"},     # ← 坑 1
  "stream": false
}
```

> **坑 1 · `thinking` 必须显式关掉**：M3 在 OpenAI 兼容接口下**默认开思考**，不关的话 `message.content` 里会混入思考过程，JSON 抽取必失败。Anthropic 兼容接口（`https://api.minimax.cn/anthropic/v1/messages`）则是默认关的。

> **坑 2 · 不要加 `response_format={"type":"json_object"}`**：MiniMax 文档中 `response_format` 只对图像生成（url/base64）有定义，文本 JSON 模式未承诺。靠 `extract_json_object()` 兜住。

> **坑 3 · 图片块格式两套不通用**：OpenAI 兼容用 `image_url` + **data URL**；Anthropic 兼容用 `{"type":"image","source":{"type":"base64","media_type":...,"data":<裸 base64>}}`（不是 data URL）。

### 5.2 限制（文档值，代码里已按此校验）

| 项 | 限制 |
|---|---|
| 图片格式 | JPEG / PNG / GIF / WEBP |
| 单图大小 | ≤ 10 MB |
| JSON 请求体 | ≤ 64 MB（base64 比原文件大约 33%） |
| 响应错误 | `base_resp.status_code != 0` → `base_resp.status_msg` |

### 5.3 JSON 抽取必须鲁棒

模型输出的实际形态包括：裸 JSON、` ```json ` 围栏、带解释文字、尾注、前后噪声、字符串里含 `}`。
`extract_json_object()` 的顺序是：**代码块 → 首个配平的 `{...}`（跳过字符串字面量里的花括号）→ 整段**。

### 5.4 不编造数据（红线）

| 场景 | 行为 |
|---|---|
| 离线（`--offline`） | 油量/金额**留空**，`status=offline` —— 绝不填假数充数 |
| 无 key / 无网 | 同上 + `warnings[]` 记录原因 |
| 油量越界（>2000 L 或 ≤0） | 判 `failed`，**不修不补**（OCR 常把 65.5 读成 655 或 6.5） |
| 识别不出 | `status=failed`，`errors[]` 记原因，其余图片继续处理 |

依据 `docs/42 §3.1`「不得为填满字段而编造发票、客户或业务记录」。
注意这与 `tools/route_fetch.py` 的 `--offline` **不同**：路线可以退回 haversine 近似值（口径明确、标注为近似），**发票金额和油量没有合法的近似值**。

## 10. 通用财务发票碳核算（v1.2）

### 10.1 算法顺序：每张票只走一个主方法

```text
票面品名 / 显式类别
        ↓
有有效实物量？── 是 ─→ 活动数据法：数量 × 活动因子
        │ 否
        ↓
有该类别已审核金额因子？── 是 ─→ 支出法：金额 × kgCO2e/CNY
        │ 否
        ↓
needs_review：排放量留空，不按 0、不套万能系数
```

| 类别 | 活动数据 | 当前活动因子来源 | 范围拆分 |
|---|---|---|---|
| 柴油 | `fuel_liters` 或 `quantity + unit=L` | `calc_factors.json` 柴油 TTW/WTT | TTW → 范围一；WTT → 范围三 |
| 外购电力 | `quantity + unit=kWh/千瓦时/度` | `calc_factors.json` 全国电力因子 | 范围二（位置法） |
| CNG | `quantity + unit=m3/立方米` | `calc_factors.json` CNG TTW/WTT | TTW → 范围一；WTT → 范围三 |
| 运输服务等其他类别 | 无可用实物量时 | `invoice_spend_factors.json`，**默认为空** | 通常范围三，由因子登记 |

核心入口：

- `calculate_invoice_carbon(record)`：单张核算；返回方法、活动量、因子来源、范围拆分、排放量、假设与警告；
- `calculate_invoice_batch(records)`：批量去重、冲突复核、按方法/类别/范围汇总；
- CLI 每张票新增 `carbon_status / carbon_method / co2e_kg / carbon_scope / included_in_total` 等列，报告新增不含业务明细的 `carbon_summary`。

活动数据法优先于支出法；两种方法**不相加**。`emissions_kg_co2e is None` 表示未核算，不能当作真实零排放。

### 10.2 支出法因子契约

`config/invoice_spend_factors.json` 的 `factors` 默认 `{}`。新增因子按 `emission_category` 登记，且必须同时具有：

| 字段 | 要求 |
|---|---|
| `value` / `unit` | 正数 / `kgCO2e/CNY` |
| `source` | 可核查数据库、文献或供应商来源 |
| `price_year` | 因子价格年；与发票年不同只警告，不自动做通胀调整 |
| `price_basis` | `including_tax` 用价税合计；`excluding_tax` 用不含税金额，二者不得混用 |
| `scope` / `gas_coverage` | 核算范围 / 气体覆盖范围 |

金额缺失、币种非人民币、因子来源或价格口径不全，都转人工复核。不得用“行业经验值”填满因子库。

### 10.3 去重与完整性

- 去重键：`invoice_code + invoice_no + seller_name`；无发票号码不猜重复；
- 键和关键字段均一致：首张计碳，其余 `excluded_duplicate`，排放量留空；
- 同键但金额、日期、品名或数量冲突：整组 `duplicate_conflict`，全部不计入合计；
- `total_emissions_kg_co2e` 只是已核算行小计；只要仍有待复核行，`total_complete=false`；
- 范围汇总直接累加 `scope_breakdown_kg`，因此方法、类别、范围三个视角均可与总量对账。

### 10.4 当前边界

1. OCR 契约按**单条有效明细**处理；多行明细不得由模型合并数量，需先拆行；
2. 红字/负数发票不在当前 OCR 契约内，须先经财务红冲流程处理，算法不取绝对值；
3. 柴油/CNG 的范围一默认以企业自有或控制设备消耗为前提，转售等场景须调整边界；
4. 电力按位置法，未处理绿电环境属性；HVO 暂不直接计碳，待补充生物源燃烧碳披露口径；
5. 发票结果仍是独立情景核算，**不自动并入 E₀、kpi 或闸门**；与运单主账联合披露前必须另做重叠边界检查。
