# 48 · 高级滑条与联动可视化图（Slider Lab）

> 施工记录：把全应用仅存的两个原生滑条重做成暗色电影感语言的高级控件，
> 并在旁配一张随滑条实时联动、可操作的可视化图。
> 配套代码：`app/components/slider_kit.py`；验收脚本：`tools/verify_sliders.js`。

---

## 1. 为什么要重做：根因不是审美，是 DOM 变了

Streamlit 1.4x 起，`st.slider` 的实现从 baseweb 换成了 **react-aria-components**。
旧控件长这样：细线轨道 + 小圆点 + 一行数字。真正的麻烦在 `theme.py`：

```css
/* 旧写法（现在完全落空） */
[data-testid="stSlider"] [role="slider"] { ... }
[data-testid="stSlider"] [data-baseweb="slider"] div[role="track"] { ... }
```

react-aria 的 DOM 里**没有 `[role="slider"]`，也没有 `[data-baseweb="slider"]`**。
实测结构（CDP 抓取）：

```html
<div data-testid="stSlider">
  <label data-testid="stWidgetLabel">…</label>
  <div role="group" data-orientation="horizontal">
    <div data-orientation="horizontal" style="position:relative">
      <div />                                   <!-- 轨道 -->
      <div style="position:absolute; left:18.36%; transform:translate(-50%,-50%)">
        <div style="clip:rect(0,0,0,0)"><input type="range" …></div>   <!-- 隐藏 input -->
        <div data-testid="stSliderThumbValue">100</div>                 <!-- 数值气泡 -->
      </div>
      <div data-testid="stSliderTickBar">…</div>                        <!-- 刻度尺 -->
    </div>
  </div>
</div>
```

所以之前所有「给滑条调色」的 CSS 都没生效，控件一直是浏览器默认长相。

## 2. 设计调研结论（2026-10 上网查证）

| 来源 | 采纳的要点 |
|---|---|
| Radix / shadcn Slider | 三段式 track + indicator + thumb；旋钮用 **ring**（box-shadow）而不是 border |
| Carbon Design System | 刻度尺与当前值同层；刻度是参考锚点，不只是装饰 |
| Apple HIG | 拖拽时旋钮放大、轨道高光跟随；命中区要大于视觉尺寸 |
| 玻璃拟态滑块实践 | `backdrop-filter` 只用在滑块自身，**不要放在轨道父级**（每帧重算模糊，帧率崩）；模糊半径 ≤ 10px；旋钮用 `will-change: transform` 提升到独立合成层 |
| 无障碍 | `aria-valuemin/max/now` 必须随值更新；键盘（←/→/PageUp/PageDown/Home/End）要等效 |

## 3. 架构：载体滑条 + 自绘滑条 + pointer 桥接

Streamlit 的 `st.slider` 有两个硬约束：**值只能由它自己产生**，且**只在 pointerup 时提交**
（`onChangeEnd`），拖动过程中拿不到中间值 —— 这就没法做"拖动时旁边的图实时联动"。

于是拆成三层（`app/components/slider_kit.py`）：

```
┌─ 父页面（Streamlit 文档） ───────────────────────────────┐
│  ① 载体滑条 st.slider(key=…)                                │
│     · Streamlit 认识的值来源                                │
│     · CSS 隐藏：opacity:0 + position:absolute + left/right:0 │
│     · 保留可测量宽度（坐标→数值映射依赖它）                 │
│                                                            │
│  ② st.iframe（iframe，与父页面同源） ─────────────────────┐
│     · 自绘滑条：玻璃轨道 + 渐变填充 + 发丝环旋钮 + 数值气泡  │
│     · 手写 SVG 图：hover 十字线 + 浮层 + 点击写值            │
│     · 拖动时 60fps 本地更新，不走服务端往返                 │
│                                                          │
│  ③ 桥接：松手时向 ① 派发真实 pointer 事件 ────────────────┘ │
│     pointerdown + pointerup 落在轨道对应位置                │
│     → react-aria 按原生逻辑算出值 → Streamlit 收到 → rerun │
└────────────────────────────────────────────────────────────┘
```

**嵌入方式用 `st.iframe` 而不是 `st.components.v1.html`**：后者已被 Streamlit 标记弃用
（"will be removed after 2026-06-01"），而 `st.iframe` 的官方文档明确保证
"HTML 字符串会以允许 JavaScript 执行、且允许同源访问 Streamlit 应用的方式嵌入"——
这正是本组件桥接所依赖的能力。代码里保留了对旧版本的回退：

```python
def _embed_html(html: str, height: int) -> None:
    if hasattr(st, "iframe"):
        st.iframe(html, width="stretch", height=height)
    else:  # pragma: no cover - 兼容 Streamlit < 1.66
        components.html(html, height=height, scrolling=False)
```

> 已知遗留：`app/components/route_map.py`（高德地图）仍用 `components.v1.html`。
> 它不依赖同源访问（JS 只在自己 iframe 内跑），但**迁移前无法离线验收**——
> 地图只在有路线结果且能连通高德时才渲染，本地跑不出该状态，
> 所以没有盲改。Streamlit 升级时记得连它一起处理。

**为什么不自绘 `<a>`/直接改 React 状态**：桥接走的是标准 DOM 事件冒泡，和用户真实拖拽
完全等价，不依赖任何 React 内部 API，Streamlit 升级也不容易碎。

### 落点坐标怎么算

优先**用旋钮的实际渲染位置反推映射比例**——react-aria 正是用它把值画到轨道上的，
所以算出来的落点与 react-aria 自己的换算完全一致：

```
scale = (旋钮中心 x − 轨道左边缘 x) / 当前值对应的比例
x(目标值) = 轨道左边缘 x + 目标比例 × scale
```

退而求其次才用轨道宽度线性换算；再不行用两点割线法现场标定。

## 4. 踩过的坑（务必记住）

### 坑 1：React 18 是异步批处理，**同步读值永远是旧值**

最早写的是 `probe()` 里派发事件后立刻 `input.value` 读回来。读到的永远是旧值，
于是割线校准用一组过期数据乱算，把值推到了越界位置（实测出现 `-100`、`500`）。
**必须 `await sleep(150~200)` 等一拍再读。**

### 坑 2：隐藏载体滑条不能用 `display:none` / `visibility:hidden`

那样滑条没有布局盒，轨道宽度为 0，坐标→数值映射直接失真。
正解：`opacity:0` + `position:absolute` + `left:0;right:0`（容器 `position:relative`）。
既不占位、不可见、不吃指针，又保留可测量的布局宽度。

### 坑 3：`st.markdown` 里的 `<script>` 根本不执行

DOMPurify 会剥掉 `<script>`。想验证过：`.stMarkdown script` 数量为 0。
JS 只能走 iframe（`st.iframe`，或旧版的 `components.html`）。

### 坑 4：iframe 里 `{{ }}` 花括号

`LAB_CSS` 里的 CSS 最初按 `.format()` 的习惯写了 `{{`/`}}`，但注入时用的是
`.replace()`，导致整份样式表语法失效——页面渲染成一堆裸文字，SVG 默认黑块。
**注入前必须 `.replace("{{","{").replace("}}","}")`。**

### 坑 5：iframe 与父页面是否同源，必须实测

`st.iframe`（及旧版 `components.html`）的 iframe 与父文档同源
（`window.parent.document` 可访问），桥接方案才成立。
**换 Streamlit 版本或换嵌入 API 时必须重新验这一条**——
本次迁到 `st.iframe` 后用 `verify_sliders.js` 重跑，值回传依然是精确命中。

### 坑 6：表单里的滑条不会实时联动

Streamlit 的 `st.form` 会把控件值按批次提交，拖动过程不触发 rerun。
所以碳价滑条必须**移出表单**（`route_sandbox` 里放在控制台面板之前），
表单提交时再从 `session_state` 取值。

## 5. 两张联动图的口径

图上的每个数都来自真实快照，**不造数**。

### 硬件监控页 · 监测窗口预览

- 数据：`live_services.sensor_data()`（`sensor_data.csv`），无真实数据时用确定性演示序列
- 纵轴：CO2 浓度（ppm）；横轴：读数时间
- 阈值线：1000 ppm（CO2 预警线）
- 高亮窗口：右侧渐变遮罩 = 「最近 N 条」，随滑条实时移动
- **可操作**：hover 出十字线与浮层（时间 + ppm）；**点击图上任意位置**可把窗口右端定位到该读数

### 路线沙盘页 · 碳价敏感度

- 数据：`demo_state.carbon_snapshot()`（与碳台账页同一口径）
- 三条线：
  - 配额抵扣额度 = 当期配额(t) × 碳价（画成面积）
  - 当期全额碳成本 = 当期总碳排(t) × 碳价（情景口径：假设全部碳排都按碳价计价）
  - 配额缺口采购成本 = 配额缺口(t) × 碳价
- **可操作**：hover 出该碳价下的金额；**点击图上任意位置**直接设定碳价

> 配额抵扣额度与全额碳成本在数值上常常完全重合（配额恰好等于总排），
> 所以前者画成面积而不是线——否则会变成两条看不见的重合线。

## 6. 演示数据纪律

没有 `sensor_data.csv` 时，`live_services.sensor_data()` 回退到一段**确定性**演示序列
（固定随机种子，日内潮汐 + 三次超标尖峰），并且：

- 页面顶部显式标注「演示数据，当前为确定性演示序列（未接入真实 ESP32），不代表现场读数」
- 图的副标题同样带「演示数据，非真实传感器读数」
- `SENSOR_MOCK=0` 可关闭演示，回到「等待传感器数据」状态

这条对齐 `src/invoice.py` 的 MOCK 纪律：演示数据必须带标记，页面必须显式说明。

## 7. 验收

```bash
python -m pytest tests/ -q                                   # 217 passed, 1 deselected
node tools/verify_sliders.js http://localhost:8501 _shots     # 滑条专项
node tools/verify_pages.js   http://localhost:8501 _shots     # 五页回归
```

`tools/verify_sliders.js` 不止截图，它会**真的拖一次滑条**并校验：

| 判据 | 含义 |
|---|---|
| 载体滑条 `opacity` 为 0 且宽度 > 0 | 隐藏了但没把布局也藏掉 |
| iframe 内 `.sl-track` 存在、SVG 有节点 | 自绘滑条与图都渲染了 |
| 拖拽后载体 `input.value` 改变 | 桥接真的写回了 Streamlit |
| 拖拽后载体值 == 拖拽位置换算的期望值 | 坐标映射精确，不是"差不多" |
| iframe 读数气泡 == 载体值 | 前后端显示一致 |

当前结果：

```
OK   sensor  carrier 100 → 360 (期望 360) | 气泡 100 → 360 | 图节点 40/40 | 隐藏=0 宽=862
OK   routes  carrier 100 → 120 (期望 120) | 气泡 100 → 120 | 图节点 35/35 | 隐藏=0 宽=1320
```
