# 企业级演进路线图：从"能演示"到"企业级"

> **性质**：咨询/规划文档，**不含任何代码改动**。
> **依据**：2026-10-27 对仓库的实读（模块清单、`data/processed/gate_report.json`、`data/processed/run_log.json`、`.github/workflows/ci.yml`、`requirements.txt`、`git status`）。
> **关联**：`docs/17` 蓝图 v3.0 ｜ `docs/22` 进度审计 ｜ `docs/25` 国赛路线图（已判定"可推广性 = 最大短板"）｜ `docs/43` 版本拆分（V1.0 明确"无登录"）｜ `docs/47`/`docs/48` 前端 v2 与滑条。

## 0. 一句话结论

**最难的部分你们已经做完了**——契约、闸门、血缘、只读边界、217 项回归测试，这些是大多数"企业级"项目最缺、也最难补的地基；
**缺的恰恰是最"无聊"的那一层**：身份与权限、持久化数据库、任务调度、可观测告警、容器化发布、备份恢复。

所以企业化的路线不是"重写系统"，而是**把已经算对的东西，放进一个能被别人安全地、稳定地、并发的使用的运行时里**。
建议顺序：**P0 交付形态 → P1 数据平台化 → P2 身份与权限 → P3 产品闭环**，每阶段都有可验收的硬判据。

## 1. 先量一下现在站在哪

### 1.1 成熟度尺子

| 级别 | 定义 | 判据 | 本项目现状 |
|---|---|---|---|
| **L0** | 脚本/笔记本 | 手工跑，出 CSV | — |
| **L1** | 单机工具 | 一个人在自己机器上跑，文件即数据库 | ✅ **当前主形态**（单机/内网，`启动.bat`） |
| **L2** | 部门级服务 | 多人共用、有身份、数据持久化、有发布流程 | ⚠️ **局部达到**：有 CI、有契约、有测试，但无身份、无 DB、发布靠手工 |
| **L3** | 企业平台 | 多租户隔离、审计完整、SLA/可观测、灾备演练 | ❌ 未开始 |
| **L4** | 产品化 SaaS | 对外运营、计费、弹性伸缩、自助接入 | ❌ 不建议现在追求（`docs/25` 已警告"为了显得庞大而加的功能"） |

**准确表述**：本项目是 **L1 的运行形态 + L2 的工程地基**。
地基（口径、契约、闸门、血缘、测试）已按 L2/L3 标准建设；运行时（并发、身份、持久化、发布、可观测）停在 L1。

### 1.2 已经具备的"企业级地基"——**不要重做**

| 资产 | 位置 | 企业化中的价值 |

| 硬校验闸门 | `data/processed/gate_report.json`：28 PASS / 0 FAIL / 0 SKIP，含 10 项目标值 + 18 项结构性检查 + 3 项路线检查 | 直接可当**发布门禁**：FAIL 不发布 |
| 执行血缘 | `data/processed/run_log.json`：四段耗时 14.9 s、退出码、`source=real` | 可升级为 run 级血缘（见 §3.6） |

### 1.3 缺口清单（按"会不会堵住企业使用"排序）

| # | 缺口 | 现状证据 | 不补的后果 | 优先级 |
|---|---|---|---|---|
| 1 | **无身份与权限** | 全仓无 login/jwt/oauth；`docs/43` 明确 V1.0 不做登录 | 谁都能看全部数据、谁都能改参数 | P2 |
| 2 | **无数据库**（业务数据只有文件） | `data/processed/*.parquet` + `sensor_data.csv` + `outputs/*.csv` | 传感器高频写入、单用户覆盖写、多人并发全都不成立 | P1 |
| 3 | **无任务调度** | 复算是手工 `python -m src.pipeline` 一次性执行 | 数据不会自动变新，"企业系统"变"演示系统" | P1 |
| 4 | **外部 API 无配额/限流/熔断** | `src/routing/amap_client.py` 固定 15 s 超时，无重试、无缓存、无配额账本 | 高德配额被打爆、账单失控、演示时失败 | P1 |
| 5 | **传感器接口无鉴权、CORS `*`** | `server.py:20` `CORS(app, resources={r"/api/*": {"origins": "*"}})`，POST 无密钥校验 | 局域网任意设备可伪造读数写入数据 | P0（安全） |
| 6 | **无运行时可观测** | 只有执行期 `run_log`（复算日志），无请求日志/指标/告警 | 出问题只能靠人点页面发现 | P3 |
| 7 | **发布靠手工** | CI 只跑 pytest；部署靠 `启动.bat` | 升级 = 手工操作，出错无回滚 | P0 |
| 8 | **无备份与恢复演练** | `data/raw` 不可再生，但无备份策略 | 原始数据丢了 = 全部结论不可复现 | P0 |
| 9 | **台账是覆盖写，不是账本** | `ledger.parquet` 每次复算覆盖 | 无法追溯"上个月报出去的账" | P3 |
| 10 | **依赖不锁定、无容器** | `requirements.txt` 全是 `>=`；无 Dockerfile | 环境漂移、无法交付给别人 | P0 |

## 2. 目标架构

**原则：不推翻现有分层，把"运行时"补在下面，把"服务化"补在中间，把"页面"保持只读。**

```
┌─ 接入层 ───────────────────────────────────────────────────────────────┐
│  浏览器 / 移动端 / 大屏   │  企业 SSO 反代（OIDC，账号不入本系统）    │
└──────────────────────────────────────────────────────────────────────┘
┌─ 应用层 ───────────────────────────────────────────────────────────────┐
│  ① 决策台（Streamlit，只读 results + 交互沙盘）  ← 现有 5 页，基本不动  │
│  ② 业务 API（Flask/FastAPI）：传感器接入 / 发票 OCR / 路线计算        │
│  ③ 任务服务（队列）：复算 / OCR / 路线抓取 / 进化搜索                │
└──────────────────────────────────────────────────────────────────────┘
┌─ 数据层 ───────────────────────────────────────────────────────────────┐
│  PostgreSQL（业务域：传感器时序 / 任务 / 审批 / 审计 / 台账版本链）    │
│  文件区 data/processed/runs/<run_id>/（大宽表继续用 Parquet）           │
│  对象存储（原始发票图 / 备份，带加密与留存策略）                       │
└──────────────────────────────────────────────────────────────────────┘
┌─ 治理层 ───────────────────────────────────────────────────────────────┐
│  契约 schema.py │ 闸门 gate_report │ 血缘 run_log │ 审计表 │ 数据分级    │
└──────────────────────────────────────────────────────────────────────┘
┌─ 基础设施 ─────────────────────────────────────────────────────────────┐
│  Docker / Compose │ 反向代理 + TLS │ CI/CD（构建→冒烟→灰度→回滚）     │
│  监控告警 Prometheus/Grafana │ 备份与恢复演练 │ 容量与压测             │
└──────────────────────────────────────────────────────────────────────┘
```

**关键取舍**

1. **账号不进本系统**——走企业 IdP 反代认证（`docs/43` 已定"不添加登录界面"，反代不违反该边界，且成本最低）。应用内只做**角色与数据范围**。
2. **Streamlit 继续做决策台，不做后端**。它擅长"只读结果 + 高密度可视化"，不擅长长任务、并发写入、鉴权。把它当 SPA 是误用。
3. **大宽表继续留 Parquet**（33 214 段 / 2.6 MB~2.4 MB 级），不强塞进 Postgres；进库的是**变化快、需要检索、需要留痕**的数据（传感器、任务、审批、审计、台账版本）。
4. **现有 217 项测试与 4 个验证脚本是回归网**，平台化改造全程要保持绿。

## 3. 分模块怎么继续做得更好

### 3.0 通用底座（做一次，全站受益）

| 底座能力 | 落地要点 |
|---|---|
| 配置分层 | 默认值 → 环境变量 → 配置文件 → 密钥文件；**部署清单不含明文密钥**，密钥走挂载/环境变量，并支持轮换 |
| 统一错误边界 | 每层有"失败时显示什么"的规约（现在 `services.py` 的"文件缺失→空表不抛异常"就是好范例，要推广到 API 层） |
| 统一响应体 | 所有服务接口返回 `{ok, data, meta:{request_id, run_id, source, generated_at}}`；**`source` 字段全链路透传**，页面据此标注"真实/演示" |
| 降级开关 | 每个外部依赖（高德 / OCR / DeepSeek / 传感器）有 `on/off/mock` 三态开关 + 降级后的**显式状态**，而不是静默回退 |
| 版本与变更 | 语义化版本 + CHANGELOG + 结果目录迁移说明；发布前必过闸门 |

### 3.1 首页概览（`app/components/dashboard_home.py`）

**现状**：静态读 `kpi/gate/ledger/方案表` → 指标卡 + 决策面板 + 步骤卡；已用 CDP 量盒模型做过重叠验收（`tools/verify_dashboard_layout.js` 7/7）。

**四步改进**

1. **把"信任信号"放到第一屏**：顶部常驻 `run_log.generated_at` + `gate_report.generated_at` + `source(real/mock)` + `闸门 28/28`。现在这些信息在 `docs` 和 JSON 里，页面上没有——企业用户第一眼要知道"这批数是哪次复算、是否可信"。
2. **从"概览"升级为"作业看板"**：现在决策面板是纯展示。接入三类**可行动项**：① 闸门 FAIL/SKIP 项；② 方案与目标差距（E₀ vs 目标减排）；③ 传感器越限事件。每条可点击跳转到对应页/图（`st.switch_page`）。
3. **异常优先排序**：用 `data_quality.json` + `flag_dup/flag_anomaly/flag_basis/flag_estimated` 四类标记做"待处理清单"，**按影响排放量排序**（不是按行数）——企业里"影响 12% 碳排的 3 条记录"远比"影响 0.1% 的 800 条"重要。
4. **角色化视图**（P2 后）：管理层看 E₀/成本/目标达成，车队调度看线路与约束，财务看台账与披露，审计只读。当前所有角色看到同一屏。

**验收**：首屏能回答"数据什么时候算的、过没过闸门、我该管哪三件事"；闸门 FAIL 时首页立即显红并给出定位链接。

### 3.2 发票数据感知（`src/invoice.py` + `main_views.render_invoice`）

**现状**：OCR → 解析 → 与油量/碳账对账；`MOCK_MODE`（`src/invoice.py:105`）纪律清晰，mock 结果带 `mock=True` 且页面显式标注"演示用，非真实识别"；原始发票产物已被 `.gitignore` 全挡（车牌/发票号/金额永不入库）。

**四步改进**

1. **置信度闭环（demo → 生产的第一道分水岭）**：现在的纪律是"有没有 mock 标记"；企业级要"**识别置信度 → 自动入账 / 转人工**"。返回体加**字段级置信度**，低置信字段（如金额、税号）入**待复核队列**，由人确认后才进账，而不是"识别即入账"。
2. **外部 API 成本与配额治理**：识别调用要有次数/金额预算、**同发票号+金额去重缓存**、失败重试与退避、超额熔断。现在是同步单次调用。
3. **异步化（做请求线程的解耦）**：Streamlit 请求线程里做网络识别 = 用户盯着转圈。企业级应"提交 → 队列 → 后台识别 → 结果可取 → 通知"。这直接依赖 P1 的任务队列。
4. **数据分级与留存**：原始发票图（含车牌）落对象存储**加密**、设留存期限、访问记审计、导出默认掩码车牌；原始图与结构化结果分离存储。发票数据当前**是否允许出内网**需 PM 拍板（影响存储选型）。

**验收**：低置信自动进复核队列且可追溯；重复发票不重复计费；任何一条入账记录可回到原图与识别原文。

### 3.3 云边端硬件监控（`server.py` + `src/telemetry.py` + `live_services.py`）

**现状**：ESP32 → `POST /api/upload_sensor` → 追加 `sensor_data.csv`（线程锁）；字段校验完整（device_id 长度、co2 ∈ [0,100000]、temp ∈ [-50,100]）；`src/telemetry.py` 契约把 PM 严格隔离在碳账之外（"测什么标什么，不折成碳"）；页面与图副标题均标注演示序列；1000 ppm 阈值以线呈现。

**五步改进**

1. **设备身份与准入（P0，安全敞口最明确）**：当前任意局域网设备可 POST。加**设备注册表**（`device_id` → 密钥/证书），请求签名校验，非法设备 401；CORS 从 `*` 收敛到实际来源。
2. **文件 → 时序存储（P1）**：CSV 追加在多设备高频下不可用（无分片、无压缩、无保留策略、查询需全量读）。建议 Postgres（+Timescale 或定期归档）+ **原始读数 TTL（如 90 天）**、长期只留窗口聚合（与 `telemetry.py` 的采样窗口径天然对齐）。
3. **断网续传与乱序**：现在 `timestamp` 由**服务端**生成（`server.py:45`），设备断网补传必然失真，重复上传会产生重复行。企业级：设备端带 **时间戳 + 序号 + 设备密钥**，服务端幂等去重 + 乱序容忍 + 迟到数据标记。
4. **固件与远程配置**：采样率、阈值、固件版本、灰度升级批量下发；阈值目前写死在页面代码里。
5. **设备健康度 + 告警闭环**：企业客户最关心的其实是"这台车今天在线吗"——加**设备级健康看板**（在线率、丢包率、异常读数率），并把 1000 ppm 越限从"一条线"升级为"**越限 → 告警 → 处置记录 → 复盘**"闭环。

**验收**：未注册设备 100% 被拒；断网 24 h 后补传数据不重不乱；越限事件产生可追踪的处置记录。

### 3.4 减碳路线沙盘（`app/components/route_sandbox.py` + `src/routing/*`）

**现状**：高德 JS API 2.0 地图（`route_map.py`）、碳价滑条 + 三线敏感度图（滑条已移出 `st.form` 以支持实时联动）、Q-learning + NSGA-II 进化、离线兜底、真实路线覆盖 **295/310（95.2%）**；已发现 `route_sandbox.py:175` 硬编码 `seed=42` 时 ε 探索退化（Q 表只填 `[0][0]`，第 3 代变异率撞下界 0.05 后不动），换 `seed=7` 正常。

**五步改进**

1. **外部 API 配额与缓存治理（P1）**：现在点一次图发一次高德请求。企业级需要：按 **OD 对 + 因子版本** 的路线结果缓存、请求队列化、日配额看板、限流与熔断、失败显式降级到离线基线（兜底已有，但要从"静默回退"变成"带状态标识的降级"）。
2. **把算法变成"可复现的离线实验"（P1，最值钱的一步）**：把训练从"页面里点一次"改为**离线实验任务**：固定输入集 → 多 seed 批量跑 → 记录每次的 **Q 表 / 动作分布 / 收敛曲线 / 耗时** → 模型版本号 → **晋级门槛**（如"动作覆盖率 ≥ 0.9 且收敛步数 ≤ N"才允许上线到页面）。一次性解决"页面跑算法不可复现"与"算法质量无人把关"两个问题，也把上一轮发现的 seed 退化变成**可被门槛自动拦下的**问题。
3. **沙盘与真实账的隔离要更硬**：现在沙盘碳价是局部情景参数、不写全局（方向正确）。企业级加**情景快照**（参数 + 代码版本 + 因子版本 + 时间 + run_id），保证任何一条结论可完整回放；沙盘结果**永不进台账**，页面上带显式水印。
4. **多人并发**：现在 Streamlit `session_state` 每会话一份，多人同时跑进化搜索会互相抢 CPU/内存。企业级：长任务入队 + `task_id` 取回 + 并发上限。
5. **前端 key 治理**：高德 JS API 需要 JS key + `securityJsCode`（前端暴露）。企业级要配**域名白名单**、key 配额归属到主体，并注意"对外发布"时的 key 泄露面。

**验收**：同一 `seed + 输入集` 100% 复现同一 Q 表；高德配额耗尽时自动降级且页面明示；沙盘结果无法流入台账（技术拦截，非约定）。

### 3.5 碳核算与台账（`main_views.render_ledger` + `src/disclosure.py` + `ledger.parquet`）

**现状**：台账六字段、披露六要素、因子版本号（`factor_version`）、双轨碳（`kg_co2` / `kg_co2_phys` + `delta_pct`）、闸门同源自校验（台账总碳 = 首页总碳）、`data/processed/fleet_audit_trail.json` 审计轨迹。

**四步改进**

1. **台账从"结果表"升级为"账本"**：现在 `ledger.parquet` 每次复算覆盖写。企业级要求**只增不改（append-only）**：每次复算产出版本链 `ledger@v1/v2…`，每行带 `run_id`、`period`、`boundary`、`factor_version`、生成时间、审批状态；修正用**红字冲正分录**，不做物理覆盖。
2. **编制 → 复核 → 批准 三态审批**：批准后的版本不可修改，只能出修订版；审批人/时间/意见落审计表，并可回放"当时用的是哪版因子、哪版代码"。
3. **对外披露与第三方核查**：把披露六要素映射到 GHG Protocol / ISO 14064 / GB-T 32150 条目；一键导出**证据包**（披露报告 + 因子快照 + 计算脚本版本 + 闸门报告 + 原始数据指纹），满足客户审厂与核查方取证的格式要求。
4. **披露自动化与时效**：按期间自动生成 + 到期提醒 + 变更留痕；现在披露是静态页。

**验收**：任意历史期间的台账可原样重现；核查方拿到的证据包能独立复算出同一个 E₀。

### 3.6 引擎层 `src/`（被所有模块依赖）

1. **幂等 + 版本化 run（地基，建议 P0 就做）**：现在 `python -m src.pipeline` 产出**固定文件名覆盖**。引入 `run_id = 时间戳 + 代码版本 + 输入指纹`，产出 `data/processed/runs/<run_id>/`，"当前生效 run"用一个指针文件表示。→ 所有"多版本、可追溯、可回放"能力都建立在这上面；**越早做越省事**。
2. **闸门从"事后打印"变成"发布门禁"**：28 项闸门抽成可被 CI / 调度器复用的校验入口；**FAIL → 不发布、不更新生效指针**，并把 `gate_report.json` 挂到发布记录上。现有闸门逻辑已是"目标值 vs 实测值、互不循环"，直接复用。
3. **计算与存储分离**：把 `pipeline` 里的"算"抽成纯函数服务、"存"抽成仓储层。**这是能不能把计算搬进任务队列的分水岭**，也是单测能覆盖算法而不用起服务的关键。
4. **参数与因子的治理闭环**：`factor_version` 已有，补"参数变更审批 + 参数随 run 固化 + 历史结果按当期参数重放（时间旅行）"。
5. **性能**：当前全量复算 14.9 s（`run_log.total_seconds`），规模尚可，多车队/多城市/高频后需增量计算 + 列式引擎（duckdb/polars）——**需 PM 放开依赖约束**。

## 6. 四条不可破的红线（平台化过程中尤其要守住）

1. **口径零改动 + 闸门先行**：任何平台化改造不得改变 E₀/KPI/台账的计算结果；所有改造必须仍然通过同一套 28 项闸门，**且 FAIL 不得发布生效版本**。
2. **Mock 纪律与通道隔离**：演示/mock 数据必须显式标注（`invoice.py` 的 `MOCK_MODE`、`live_services.sensor_is_mock()`）；实时演示通道的结果**永不**进入 E₀ / KPI / 闸门 / 台账。
3. **原始数据永不入库 + 数据分级**：`data/raw` 不入 Git、不进结果区；发票/车牌级敏感数据加密留存、导出脱敏、最小权限、可审计。
4. **令牌唯一真源**：视觉令牌仍只认 `app/components/theme.py` 的 `:root`；新增页面/组件不得另起 CSS 变量。
