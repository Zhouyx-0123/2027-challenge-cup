## 1. 交付是什么

22 个文件，形态是 **Excel 工作簿 + 阶段说明文档**，按 A0–A6 组织：

| 阶段 | 产出 | 回答的问题 |
|---|---|---|
| A0 | 输入清单、来源登记表 | 输入有哪些、缺什么、依据可不可追溯 |
| A1 | 规则卡 v2 | 按什么算、算到什么边界、单位怎么定、缺失重复怎么办 |
| A2 | 字段字典、活动数据模板 | 一条活动记录有哪些字段、必填与缺失规则、财务账怎么映射 |
| A3 | 排放源清单、范围划分 | 哪些算 Scope 1/2、哪些不算、为什么 |
| A4 | 碳账主表、配额台账 | 逐趟排放量、配额结余/缺口 |
| A5 | 证据索引 | 每一行排放对应的凭证在哪 |
| A6 | 自检、测试、交付说明 | 这些结论可不可信 |

**核心特征**：这是一套**带门禁的台账体系**，不是一份报表。
它有主项目目前缺的三样东西：

1. **人工审批门禁**（`Owner_Approval_Status`）—— 公式不能替人批准；
2. **正式汇总资格**（`Formal_Summary_Eligibility=FORMAL_APPROVED`）—— 汇总不是"把明细加一遍"；
3. **证据链**（`Evidence_ID` ↔ `run_id` ↔ 主账行号 ↔ 凭证）—— 每行排放可回溯。

## 3. 口径对齐：TTW vs WTW（**最要紧的一件事**）

### 事实

对方碳账主表 `Trip_Detail` 的柴油因子：

```
EF_Value = 3.16 kgCO2e/L      Factor_Status = proxy_pending_verification
```

本项目 `config/calc_factors.json`：

```json
"diesel_ttw_kg_per_l": 2.63   ← GB/T 2589 / IPACC，尾管排放
"diesel_wtt_kg_per_l": 0.53   ← EN 16258 附录 A，上游生产+运输分摊
```

**2.63 + 0.53 = 3.16** —— 对方的 3.16 正是本项目已登记的 **WTW 全生命周期**合计值。

电力侧同样吻合：对方 `0.5568 kgCO2e/kWh` = 本项目 `grid_wtt_kg_per_kwh = 0.5568`（生态环境部 2023 年度全国电力平均 CO₂ 排放因子）。

### 结论

**对方碳账整体是 WTW 口径，本项目 E₀ 主账是 TTW 口径。**
两者相差 +20.2%（3.16 / 2.63），**这不是错误，是核算边界差异**。

对方文档把 3.16 标为"由 PPT 示例反推的代理参数"，这个说法**低估了它**——
它恰好等于本项目 config 里两个已登记因子之和，与 electricity 因子来源一致。

### 为什么必须处理

如果两边都出数、都不标注口径，评委或财务负责人对账时会看到 **20% 的"偏差"**，
然后花大量时间去查一个**根本不存在的数据错误**。这是最容易在答辩现场翻车的一类问题。

### 处理建议（待负责人拍板）

**建议方案：两边并存 + 显式标注，不改任何一边的口径。**

1. 对方主账增列 `EF_Basis`（`TTW` / `WTW`），因子登记表同步登记；
2. 本项目披露附注里已区分 `factor_source`，把 WTW 分摊单列一行；
3. 对账规则固定为：

   ```
   本项目 E₀ (TTW) + 上游分摊 (WTT) = 对方 WTW 口径
   ```

   上游分摊本项目已有因子（`diesel_wtt_kg_per_l`），桥接不需要新数据。

**不建议**为了对齐而把任意一边改成另一边的数 —— 那是改口径，比 20% 的差异严重得多。

## 4. 字段对接：工程侧 → 碳账侧

对方 `Activity_Data` 模板 51 列。逐字段对工程侧的现有数据：

| 对方字段 | 工程侧来源 | 状态 |
|---|---|---|
| `distance_km` | `baseline_carbon.parquet` / 段表 `dist_km` | ✅ 直接可用 |
| `cargo_t` | 段表 `load_t` | ✅ 直接可用 |
| `speed_kmh` | 段表 `speed_kmh` | ✅ 直接可用 |
| `vehicle_tare_t` | 段表 `vehicle_type` / `vclass` | ⚠️ 需映射到整备质量 |
| `trip_date` / `activity_month` / `activity_year` | 段表 `complete_ts` | ✅ 可用 |
| `waybill_id` | 段表 `waybill_no` | ✅ 可用 |
| `segment_id` | 段表派生 | ✅ 可用 |
| `trip_id` | 段表 `trip_id`（物理趟次） | ✅ 可用（物理趟次去重指纹正好对上） |
| `vehicle_id` | 段表 `plate`（**需脱敏**） | ⚠️ 脱敏规则 |
| `factor_value` | `config/calc_factors.json` | ✅ 唯一真源，但见 §3 口径 |
| `factor_source_row` | 对方 `source_register.xlsx` 行号 | ⚠️ 本项目因子需登记进来源表 |
| `run_id` | `data/processed/current_run.json` 的 `run_id` | ✅ 直接可用 |
| **`activity_value`（燃油 L / 电力 kWh）** | **见下** | ❗**核心缺口** |
| `evidence_id` / `invoice_no` | 发票台账 `outputs/invoice_ledger.csv` | ⚠️ 需接线 |
| `owner_approval_status` | — | 人工填写（这是设计如此） |

### 核心缺口：活动量从哪来

对方碳账的核心输入是**活动量**（消耗了多少油/电）。而本项目 E₀ 主链路走的是
**里程 × 排放因子**，**不需要活动量**——因子法算不出"烧了多少"。

三条候选来源，本仓库现在都有或快有了：

| 来源 | 状态 | 产出 |
|---|---|---|
| 发票油量 | ✅ 已有 | `src/invoice.py` + `outputs/invoice_ledger.csv` |
| **OBD 实测油耗** | ✅ **本轮刚做完** | `src/obd_gps.py` → `data/processed/obd_vehicle_carbon.parquet` |
| 电量 | ❌ 无 | 纯电车走电网因子，但没有电表采集通道 |

**OBD 实测通道正好补上这一环**，而且它给出的就是「每台车实时油耗」，
可以直接填进 `activity_value`，并成为对方 `EF_Value` 的**实测校准锚点**。

> 这正好接上吴老师那句话：「你测的和这些估的能不能对得上；对不上，估的可能就不用了。」
> OBD 实测 → 对方 Activity_Data → 因子校准 → 回写 `config/calc_factors.json`，
> 是一条闭环的路径。

### 第二步（建议下一轮）

**做适配器，不改口径**：

1. 写一个只读转换器，把工程侧段表 + OBD 实测（或发票）油耗，映射成
   `Activity_Data` 的 51 列，产出待填的底稿（**不写正式汇总**）；
2. 字段字典里补上 `run_id` 与 `factor_source_row` 的登记规则；
3. 配一个对账脚本：工程侧 TTW 排放 vs 碳账侧 WTW 排放（加上游分摊后）
   —— 这一步能验证两个体系接得上。

### 第三步（正式化，依赖外部资料）

1. 正式排放因子文件到位 → `factor_status` 从 `proxy_pending_verification` 改为已核验；
2. 真实凭证（发票、运单、装置读数、run logs）到位 → `evidence_index` 指向真实文件；
3. 负责人逐行填 `Owner_Approval_Status=approved` → 正式汇总从 0 行变为有数；
4. 国家标准全文到位 → 规则卡冻结，条款号与公式逐条映射。
