# 路段主表与聚合口径（trip_proxy v1）

> 2026-11-06。回答“5 档为主、3 簇并列”落地后，**按什么粒度聚合、哪些数能加、平均速度到底报哪一个**。
> 对应产物：`data/processed/jd_segment_master.parquet`（12,167 行 × 29 列）、
> `data/processed/jd_segment_master_audit.json`。

## 0. 一句话结论

- **一行 = 一趟京东运单合并后的 trip**，不是同一趟内切出的多个真实道路片段。
  字段 `grain="trip_proxy"`、`segment_scope="whole_trip"`、`has_subtrip_trajectory=False` 写死。
- **碳值只认主账**：`carbon_kg = sum(baseline_carbon.kg_co2 by trip_id)`，合计
  **2,258,438.376 kg**，与 `kpi.json total_kg` 逐值相等（审计 `reconciliation.status="ok"`）。
- **论文 5 档是碳规则/汇报主口径**，`paper_bin` 是固定边界标签；
  **K-means 3 簇是运营画像并列层**，`cluster_id` 由速度 + 里程 + 载重得到。
  两者都**不重算碳**，主表里的 `carbon_kg` 不随分档/聚类变化。
- 聚合必须：先过滤 `passed`，再按**可加字段求和**，比率字段用“先加后除”重算；
  **不能对 `ef_g_km`、`speed_kmh` 直接求平均**。

## 1. 数据边界（先说清楚，避免把 trip_proxy 当逐秒轨迹）

| 项目 | 事实 | 影响 |
|---|---|---|
| 输入 | 33,214 条京东运单（JDVB…），去重为 12,167 趟 | 运单是财务/碳分摊的最小凭证，趟是路段主表的最小行 |
| 速度 | **只有整趟平均速度** `vsp_physical_trips.speed_kmh` | 不能在同一趟内切多个速度段；OBD 才可能提供逐秒 rpm/扭矩/油耗/怠速 |
| 轨迹 | 无逐秒 GPS 点 | 不能算真实道路坡度、拥堵段、怠速段 |
| OBD | `obd_points.parquet` 仅 6,600 点 / 2 条 demo 轨迹，`obd_summary.json` 标 `is_demo=true` | 不能拿来做统计分档；OBD 解析器/契约已就绪，等真实日志 |
| 碳源 | `baseline_carbon.kg_co2` 逐运单分摊 | 主表按 trip 求和，等于 E₀；不是按 5 档/3 簇重新算 |
| 车牌 | `plate_id` 为加盐哈希；原车牌在 `vsp_seg_plate_map` | 主表不落明文车牌 |

**为什么不做“同趟多段”**：京东数据只有一趟一个均速，硬切会把同一个速度复制成多段，
制造“段数变多、碳不变”的假精度。当前诚实口径是“一趟 = 一个 trip_proxy 路段”；
真实 OBD 日志到位后，同一套字段可以切到 `grain="segment"`。

## 7. 聚合口径（这是本文档的核心）

### 7.1 可加字段（直接 `sum`）

| 字段 | 单位 | 说明 |
|---|---|---|
| `carbon_kg` | kg | 主账 `kg_co2` 按 trip 求和；**唯一碳主值** |
| `carbon_kg_phys` | kg | 物理轨对账值；只做偏差分析，**不**与 `carbon_kg` 相加 |
| `distance_km` | km | 主账 `trip_km` |
| `duration_h` | h | 趟时长 |
| `n_waybills` | 条 | 运单数；不是碳权重 |

分组键：`trip_id`、`plate_id`、`month`、`paper_bin`、`cluster_id`
（另允许 `vehicle_group`、`vehicle_type`）。**不要手写 groupby**，用 §7.4 的入口：

```python
import pandas as pd
from src.segment_aggregate import aggregate_master

m = pd.read_parquet("data/processed/jd_segment_master.parquet")
by_bin = aggregate_master(m, "paper_bin")        # 自动过滤 131 条 invalid
by_cluster = aggregate_master(m, "cluster_id")   # 空簇保持 <NA>，不填 0
all_rows = aggregate_master(m, "paper_bin", include_invalid=True)  # 分母变成全量
```

返回列固定为 `keys + AGGREGATE_COLUMNS`（14 个指标），已含 `ef_g_km`、
三种速度、两种载重与 `carbon_share_pct`；5 档按论文顺序输出。

### 7.2 非可加字段（先加后除）

| 指标 | 公式 | 用途 | 禁忌 |
|---|---|---|---|
| `ef_g_km` | `1000 * sum(carbon_kg) / sum(distance_km)` | 车队/分组碳强度 | 不能 `mean(ef_g_km)`；短途高 EF 会按趟数放大 |
| `avg_speed_kmh` | `sum(distance_km) / sum(duration_h)` | 车队运营时间口径 | 分母是小时，长途/堵车趟权重大 |
| `avg_speed_trip_kmh` | `mean(speed_kmh)` | “典型一趟”速度；与 K-means 簇心同口径 | 不能当车队总速度 |
| `avg_speed_dist_weighted_kmh` | `sum(speed_kmh * distance_km) / sum(distance_km)` | 按公里加权 | 与时间加权不等 |
| `avg_load_t` | `sum(load_t * distance_km) / sum(distance_km)` | 吨公里口径 | 不能当“每趟平均装载” |
| `avg_load_trip_t` | `mean(load_t)` | 每趟平均装载 | 不能当吨公里 |
| `carbon_share_pct` | `组碳 / sum(valid carbon) * 100` | 结构占比 | 分母必须写清楚是 valid 还是全量 |

**速度三个口径为什么差这么多**：同一簇 0 的趟，`speed_kmh` 的简单平均是 23.572，
但 `sum(distance)/sum(duration)` 只有 14.407。原因是 `speed_kmh` 本身就是每趟
`distance/duration`（逐趟相关系数 ≈1），而简单平均对每趟等权；时间加权会让
“耗时长、速度低”的趟占更大权重。两者都不是错，**但必须标注口径**：
- 说“K-means 簇心速度 / 典型趟速度” → 用 `avg_speed_trip_kmh`（23.572）；
- 说“车队总里程除以总时长 / 运营速度” → 用 `avg_speed_kmh`（14.407）；
- 说“按公里加权” → 用 `avg_speed_dist_weighted_kmh`（25.100）。

### 7.3 聚合时的固定动作

1. **先过滤** `passed == True`（或显式保留 invalid 单列“未通过门禁”）。
2. **只加可加字段**；比率字段在聚合后重算，绝不先算每行再平均。
3. **分组键显式列出**；`cluster_id` 的 131 个空值用 `"unclustered"` 标注，
   不要填 -1 或 0。
4. **分母写清楚**：碳占比的分母是 valid 碳（2,214,933.440 kg）还是全量
   （2,258,438.376 kg）；两者差 1.9263%。
5. **不要把 `paper_bin` 与 `cluster_id` 互相替代**：5 档回答“论文规则档位”，
   3 簇回答“运营画像”；需要交叉时用 §6 的矩阵，不要强行映射。

### 7.4 可执行入口（唯一推荐）

`src/segment_aggregate.py` 的 `aggregate_master(master, by, *, include_invalid=False)`
把 §7.1–7.3 写成代码约束，调用方不需要再记公式：

| 行为 | 实现 |
|---|---|
| 过滤 | 默认只留 `passed=True`；`include_invalid=True` 才把 131 条算进分母 |
| 缺值 | `carbon_kg` 或 `distance_km` 为空的趟剔除，不按 0 计 |
| 可加字段 | `trips / n_waybills / distance_km / duration_h / carbon_kg / carbon_kg_phys` 直接求和 |
| 比率 | `ef_g_km`、三种速度、两种载重、`carbon_share_pct` 全部先加后除 |
| 分母 0 | 用 `.where(...)` 置空，不产生 `inf` |
| 排序 | `paper_bin` 按论文 5 档顺序；其他键稳定排序 |
| 非法调用 | 未知/重复分组键、缺列直接 `ValueError` |

对应测试 `tests/test_segment_aggregate.py` 6 项：invalid 排除、全量分母、
空簇不写 0、双速/双载重加权、非法键报错、列顺序稳定。真实主表复算结果与
§5/§6 完全一致：valid 12,036 趟 / 2,214,933.439918 kg / 2,111,819.46 km。

## 8. 为什么“5 档为主、3 簇并列”

- **5 档**：边界来自论文实测（0/20/40/60/80/∞，左闭右开），确定性、可审计、
  可直接写进碳规则卡/答辩材料；它回答“这趟落在论文哪个速度档”。
- **3 簇**：K-means 用速度 + log 里程 + 载重，回答“我们的运营结构自然长什么样”；
  K=3 是用户拍板，轮廓系数 K=2 更高（0.533 vs 0.422）但业务解释不足，故并列保留。
- **并列不等于等权**：主表碳值只来自主账；5 档用于规则/汇报，3 簇用于运营画像/
  异常筛查/页面分层。两者都不改 E₀、不改 28 条主闸门。
